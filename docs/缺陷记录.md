# 缺陷记录

一共执行 32 条用例，发现 5 个缺陷。

---

## BUG-001 姓名能存脚本，打开列表页会弹窗

**严重程度：严重**

复现步骤：

1. 用 admin 登录，进「新增居民」页面
2. 姓名填 `<script>alert(1)</script>`，其他字段填正常值
3. 点保存
4. 打开居民列表页

期望：列表页把姓名当普通文字显示

实际：弹出 alert 弹窗。而且这条数据已经存进数据库了，以后再打开列表页还会弹。

原因：`resident_list.jsp` 第 146 行是用 `${r.name}` 直接输出的。JSP 的这种写法不会转义 HTML，所以姓名里的 `<script>` 被浏览器当代码执行了。应该写成 `<c:out value="${r.name}"/>`。

影响：任何能新增居民的人，都能在管理员打开列表页的时候执行 JavaScript，可以拿去偷管理员的登录凭证。

## BUG-002 身份证号不校验格式

**严重程度：严重**

复现步骤：

进「新增居民」页面，身份证号分别填下面几种，其他字段填正常值：

| 填的内容 | 位数 | 实际结果 |
|---|---|---|
| `12345620000101000` | 17 位 | 保存成功 |
| `12345620000101006A` | 18 位，末尾字母 A | 保存成功 |
| `12345620000101000七` | 18 位，末尾中文 | 保存成功 |
| `12345620000101014👍` | 18 位，末尾 emoji | 保存成功 |

期望：身份证号应该是 18 位（末位可以是 X），不符合的应该被拒绝并提示格式错误

实际：上面这些全部保存成功，并且出现在列表里

原因：输入框上只有 required（必填），没有限制长度也没有限制格式。后端也没写校验，数据直接进数据库。数据库那一列是 varchar(18)，所以实际上只限制了长度不超过 18 个字，内容是什么不管。

影响：身份证号是户籍系统里区分居民的唯一标识，格式错了档案就对不上人，后面统计、比对都会出问题。

## BUG-003 姓名首尾的空格被存进数据库

**严重程度：一般**

复现步骤：

1. 进「新增居民」页面
2. 姓名填 `␣张伟␣`（前面后面各一个空格）
3. 点保存
4. 查数据库：`SELECT r_id, name, CHAR_LENGTH(name) FROM resident WHERE name LIKE '%张伟%';`

期望：系统应该自动把首尾空格去掉，存成 `张伟`（长度 2）

实际：存进去的是 `␣张伟␣`（长度 4），空格原样保留了

影响：在列表页用模糊查询搜「张伟」是能搜到的，看不出问题。但以后要做按姓名精确匹配、去重、排序、导出，这个藏起来的空格就会出问题。

---

## BUG-004 姓名只填一个空格也能保存

**严重程度：一般**

复现步骤：

1. 进「新增居民」页面
2. 姓名只输入一个空格，其他字段填正常值
3. 点保存

期望：应该拒绝保存，提示姓名不能为空

实际：保存成功，数据库里多了一条姓名只有一个空格的记录

原因：HTML 的 required 只判断值是不是空字符串，一个空格不算空字符串，所以浏览器没拦住。后端也没做非空判断，空格就直接存进去了。

影响：系统里会出现没有有效姓名的居民记录，影响数据质量。

---

## BUG-005 出错时把数据库报错原文显示给用户

**严重程度：一般**

复现步骤：

1. 进「新增居民」页面
2. 姓名填 51 个字（超过数据库那一列的上限 50）
3. 点保存

期望：给出人能看懂的提示，比如「姓名长度不能超过 50 个字」

实际：页面上用红框显示了一大段数据库报错原文，里面有：

- 表名和字段名：`resident`、`name`
- 完整 SQL 语句：`INSERT INTO resident (name, id_card, gender, birthday, phone, address, h_type, photo, account_id) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)`
- 异常堆栈：`com.mysql.cj.jdbc.exceptions.MysqlDataTruncation: Data truncation: Data too long for column 'name' at row 1`

原因：`ResidentController.add()` 里捕获异常之后执行的是 `model.addAttribute("errorMsg", "保存失败：" + e.getMessage())`，把异常对象的原文直接返回到页面上了。

影响：别人可以借助这些信息猜到数据库结构，方便进一步攻击。普通用户看到这一串也完全不知道该怎么办。

## 另外观察到的现象

### 身份证号大小写没统一

如果数据库里已经有 `12345620000101000X`（末位大写 X），再提交 `12345620000101000x`（末位小写 x）会提示重复、保存失败。

原因是这一列的排序规则是 `utf8mb4_0900_ai_ci`，里面那个 ci 表示大小写不敏感，所以唯一索引把大小写不同的值当成同一个。

这个行为在功能上确实挡住了重复，但存进去的值大小写不统一。暂时不判定为缺陷，需要跟需求确认。
